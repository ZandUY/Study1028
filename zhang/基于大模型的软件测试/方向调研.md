# 基于大模型的软件测试

| 方向           | 测试输入                                                     | 方法                                                         | 输出                                                         |
| -------------- | ------------------------------------------------------------ | ------------------------------------------------------------ | ------------------------------------------------------------ |
| 单元与回归测试 | 被测代码、仓库依赖或者已有测试和执行结果                     | 1.生成候选测试 <br />2.运行<br/>3.修复环境问题               | 可运行的单元测试或回归测试                                   |
| 需求驱动的测试 | 需求、用户故事、领域文档、页面API信息                        | **把自然语言需求逐步变成能够检查软件行为的测试<br />**1.理解并拆解需求 <br />2.设计测试场景：可能写成 Gherkin 的 `Given–When–Then`<br />3.编写可执行代码：结合项目的 API、已有步骤定义<br /> | 测试场景、测试脚本                                           |
| 测试预言生成   | 被测功能的信息、测试输入，以及说明正确行为的依据，如需求、契约或文档 | **程序运行后，用什么规则判断结果对不对**<br />从输入中推导应满足的行为，再把它表达成可执行的断言、检查 | 判断运行结果是否正确的规则                                   |
| API与GUI测试   | 需求、API 说明                                               | **交互式、边观察边行动**<br />找出接口依赖，规划请求顺序；执行请求并利用返回值决定下一步 | 多步 API 请求、测试数据及检查响应的断言                      |
| 模糊测试       | 目标程序的 API、文件格式或协议说明                           | **让模型利用格式知识构造有针对性的输入或生成工具**           | 一种是直接生成待运行的输入或测试程序；另一种是生成可反复使用的测试驱动器、输入生成器、语法规则或变异器 |
| 缺陷复现       | 缺陷报告、相关代码和运行环境；有些设置还会利用版本信息       | **从报告中找出触发条件与应有行为，构造测试并尝试运行**       | 一条能够复现该缺陷的测试                                     |
