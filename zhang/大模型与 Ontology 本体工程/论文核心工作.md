## 二、与之前工作不同之处

| 类型 | 从表格数据生成本体的方式 |
| --- | --- |
| 传统本体工程 | 本体工程师和领域专家人工理解数据，再定义类、属性、关系和公理 |
| 早期自动化方法 | 主要根据表名、列名和数据类型进行规则转换 |
| 本文 OntoGenix | 用 LLM 理解数据语义，把“数据预处理→结构规划→本体构建→映射与知识图谱生成”组成可交互工作流 |

本文的目标不是完全取代人类，而是在本体工程师面对陌生数据集时，先生成一个可修改的本体初稿。

### Agent 数量与协作方式

OntoGenix 是一个**多 Agent 工作流**，实验使用 GPT-4 `gpt-4-1106-preview`。主要角色为：

```text
Assist Bot：记录状态、理解用户意图并调度其他模块
Prompt Crafter：批判和改写用户的建模要求
Plan Sage：结合数据摘要和用户要求，规划高层本体结构
OntoBuilder：将高层结构转换为 Turtle 本体
OntoMapper：生成 RML 映射，并根据报错自我修复
```

## 三、一个简单例子

假设输入一个订单 CSV：

```csv
OrderID,CustomerID,ProductName,Country,Quantity
O001,C018,Coffee,China,2
O002,C027,Tea,France,1
```

OntoGenix 不会简单地把每一列都变成“类”，而是按以下流程处理：

```text
订单 CSV
Data Processing：识别数值、文本、分类列，生成统计摘要和唯一 URI
Prompt Crafter：把“为销售数据建模”改写成更明确的任务
Plan Sage：规划 Order、Customer、Product、Country 等类
OntoBuilder：生成 OWL/Turtle 本体
OntoMapper：建立 CSV 列到本体实体的 RML 映射
KGen：生成 RDF 三元组，并把错误返回给 OntoMapper
```

Plan Sage 可能先生成这样的概念结构：

```text
Order
├── placedBy → Customer
├── containsProduct → Product
├── shippedTo → Country
└── quantity → integer
```

OntoBuilder 再把其写成机器可读的 Turtle：

```turtle
:Order a owl:Class .
:Customer a owl:Class .
:Product a owl:Class .

:placedBy a owl:ObjectProperty ;
    rdfs:domain :Order ;
    rdfs:range :Customer .

:quantity a owl:DatatypeProperty ;
    rdfs:domain :Order ;
    rdfs:range xsd:integer .
```

这里的关键区别是：**本体定义数据的语义模型，RML 定义原始列如何填入该模型，RDF 三元组则是最终的具体数据**。

## 四、如何评估：与人类本体工程师进行比较

```text
每个数据集
OntoGenix 独立生成一个本体
人类本体工程师独立构建一个本体
   OQuaRE：19 个结构与质量指标
   OOPS!：检测本体建模陷阱
   专家定性审查：由第三位、10 年以上经验的工程师评估
   时间评估：比较从零建模与修改 OntoGenix 初稿的耗时
```

论文使用 6 个商业活动相关的 Kaggle 数据集。两位人类工程师各自建模 3 个数据集，两人都有至少 5 年本体开发经验。

| 数据集 | 行数 | 列数 |
| --- | ---: | ---: |
| Airlines Customer Satisfaction | 129,880 | 23 |
| Amazon Ratings | 2,023,070 | 4 |
| BigBasket Products | 8,208 | 9 |
| Brazilian E-commerce | 99,441 | 5 |
| Customer Complaint | 745,392 | 18 |
| E-commerce | 541,909 | 8 |

## 五、实验结果

### 5.1 生成的本体像人建的吗？

OntoGenix 会根据数据集调整建模规模，生成的类、属性和公理数量与人工本体处于相同量级，且通常包含更多内容。但“内容更多”不等于“建模更正确”。

OQuaRE 的 1–5 分质量分数显示：

| 数据集 | 人类得分更高的指标数 | OntoGenix 得分更高的指标数 |
| --- | ---: | ---: |
| Airlines | 4 | 2 |
| Amazon | 6 | 3 |
| BigBasket | 1 | 1 |
| Brazilian | 1 | 6 |
| Customer | 3 | 3 |
| E-commerce | 1 | 5 |

OntoGenix 的优势主要体现在**注释和内容丰富度**；人类的优势主要体现在**分类层次、路径设计与复杂结构**。结果还受人类工程师个人建模风格影响，因此不能把单一指标的胜负直接解读为“LLM 超过人类”。

### 5.2 最实用的结果：节省初稿建模时间

| 数据集 | 人工从零建模（分钟） | 基于 OntoGenix 修改（分钟） | 节省比例 |
| --- | ---: | ---: | ---: |
| Airlines | 369.0 | 214.6 | 41.8% |
| Amazon | 108.8 | 56.0 | 48.5% |
| BigBasket | 236.3 | 166.2 | 29.7% |
| Brazilian | 105.0 | 70.2 | 33.1% |
| Customer | 318.0 | 291.8 | 8.2% |
| E-commerce | 375.0 | 156.4 | 58.3% |
